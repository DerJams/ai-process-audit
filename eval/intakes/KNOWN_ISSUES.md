# Known issues in the current synthetic intakes

These intakes were generated by Gemini 3.1 Pro. The problems below were found after
generation and are recorded here rather than fixed in place, because correcting them
by hand in a different model would defeat the reason a different model wrote them.
A corrected set is expected from Gemini.

**Gold labelling should not begin until the corrected set lands.** Labels are tied to
a rubric version and to the intake they were written against, so labelling these and
then replacing them would throw the labels away.

All three files validate cleanly against intake schema 1.2.0. Every issue below is a
content problem that the schema cannot catch, which is itself worth noting: a schema
checks shape, not sense.

## 1. Weekly time figures on processes that do not run weekly

`hours_per_week` only means anything for a process that runs every week. Where it is
given for an occasional process, the engine multiplies it by a 48 week working year
and produces an annual figure far larger than the description supports.

| File | Process | Frequency | States | Engine reads | Description suggests |
| --- | --- | --- | --- | --- | --- |
| corner-pharmacy | `inventory-audit` | quarterly | 15 hours a week | 720 hours a year | four counts a year |
| corner-pharmacy | `tax-preparation` | annually | 2 hours a week | 96 hours a year | one annual exercise |
| bean-and-bark-roasters | `equipment-calibration` | annually | 0.5 hours a week | 24 hours a year | one annual exercise |

The fix is to state these as `minutes_per_case` instead, sized so the annual total
matches what the description says happens.

This lands directly on the return band criterion, which is scored from hours a year,
so all three would currently score too high on return.

## 2. A time figure that contradicts its own pain text

| File | Process | Issue |
| --- | --- | --- |
| boutique-landscaping | `material-sourcing` | Reports 15 hours a week, which the engine reads as 720 hours a year. The pain text describes it as wasting a Thursday morning, which is closer to 4 hours a week. |

Either the number or the prose is wrong. They cannot both be right, and a labeller
reading the prose and an engine reading the number will disagree for a reason that
has nothing to do with the rubric.

## 3. data_notes is present on one process out of fifteen

Only `green-intake` in bean-and-bark-roasters has `data_notes`. The field is optional,
so this is legal, but it is the main input to the data availability criterion. With it
missing the engine falls back to scanning the description and tool list, which is a
weaker signal than the field exists to provide.

A realistic spread would have some processes describing structured data in a named
system, some describing spreadsheets or exports, and some describing paper, photos, or
nothing recorded at all. Fourteen processes silent on where their data lives is not a
realistic spread, it is a gap.

## What this does not include

Nothing here is a judgement about whether the businesses are plausible or whether the
processes are good automation candidates. Those are the questions the gold labels are
meant to answer, and pre judging them in this file would contaminate the labelling.
